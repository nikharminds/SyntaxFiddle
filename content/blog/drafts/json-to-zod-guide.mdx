Runtime validation is the contract between "it worked on my machine" and "it works in
production". Zod is the de facto standard for that contract in TypeScript — but writing
schemas by hand for large JSON payloads is tedious, error-prone, and drifts the moment
the API changes. Generating Zod schemas from a real payload sample fixes all three.

## Why hand-written schemas drift

A hand-written schema encodes two beliefs: what the API *documents*, and what the
developer *remembers*. Neither survives contact with reality. Fields get added without
notices, types silently change from number to string, and a key that was always present
suddenly goes missing in edge cases.

A schema generated from a representative sample encodes what the API *actually returns*.
The workflow becomes: capture a response, generate, diff against the committed schema,
and review the diff in a pull request.

## From JSON payload to Zod schema

Start with a realistic payload:

```json
{
  "id": "usr_2048",
  "email": "ada@example.com",
  "profile": {
    "displayName": "Ada Lovelace",
    "verified": true
  },
  "roles": ["admin", "editor"],
  "lastLogin": "2026-09-30T14:22:10Z"
}
```

The generated Zod schema mirrors the shape exactly:

```typescript
import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  email: z.string(),
  profile: z.object({
    displayName: z.string(),
    verified: z.boolean(),
  }),
  roles: z.array(z.string()),
  lastLogin: z.string(),
});

type User = z.infer<typeof UserSchema>;
```

### Nested objects and arrays

Every nested object becomes its own `z.object`, and arrays are typed by their element
schema — `z.array(z.string())` for roles. When an array holds mixed shapes, a good
generator emits a `z.union` of the distinct element types it observed instead of
collapsing everything to `z.unknown()`.

### Zod optional vs nullable: reading the sample data

This is where generators earn their keep. The rule that matters:

- A key **missing from some objects** in the sample → `.optional()`
- A key **present but null** → `.nullable()`
- Both observed → `.nullable().optional()`

Conflating the two is a classic production bug: TypeScript treats `prop?: string` and
`prop: string | null` as different contracts, and so does Zod.

## Strict vs loose validation

By default, Zod objects strip unknown keys on parse — useful for sanitizing input, but
it hides schema drift. Compare:

```typescript
// Loose: silently drops unknown keys
const Parsed = z.object({ id: z.string() }).parse(payload);

// Strict: throws when the payload has extra keys
const Strict = z
  .object({ id: z.string() })
  .strict()
  .parse(payload);
```

At a trust boundary (public API input, webhooks), prefer `.strict()` and whitelist what
you accept. For internal services you control, stripping unknown keys is often the more
pragmatic default — new fields keep flowing instead of breaking consumers.

## TypeScript types from z.infer

Because Zod schemas are TypeScript, `z.infer` gives you static types that can never
disagree with runtime validation:

```typescript
const UserSchema = z.object({ id: z.string() });

// Static type, derived from the runtime schema — zero drift possible
type User = z.infer<typeof UserSchema>;
// { id: string }
```

If you only need the interface (no runtime validation), a direct JSON-to-TypeScript
pass emits cleaner output — optional markers, nullable unions, and named nested
interfaces — without the Zod scaffolding.

## Validate at the boundary, not everywhere

Generate once, validate once — where untrusted data enters your system: HTTP handlers,
queue consumers, webhook receivers, and environment/config loading. Passing a parsed
and typed object through the rest of the codebase is what lets `z.infer` types do
their job. Validating deep inside business logic is a sign the boundary is leaking.
